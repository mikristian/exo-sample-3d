# EXO factory ZIP resource budget: independent audit, 2026-10-24

## Scope

This document accompanies `src/core/factoryZipResourceBudgetIndependent20261024_0600.test.mjs`, a small adversarial suite against `auditFactoryZipResourceBudget20261024_0600(bytes)`. It exercises compressed six-size input, local-and-central uncompressed-size forgery, oversized declared expansion, high compression ratios, excessive entry counts, `Uint8Array` views with nonzero byte offsets, malformed input, and byte preservation. An `ok: true` result only indicates acceptance by a development-time archive guard. It never grants manufacturing approval.

## Existing guard boundaries inspected

The ZIP envelope (`factoryZipEnvelope20261024_0154.mjs`) limits the archive to 512 MiB, the entry count to 2,048, declared total uncompressed sizes to 512 MiB and declared per-entry output to 256 MiB. It checks local/central header consistency, offsets, paths, unsupported flags, ZIP64, and overlap. The metadata guard (`factoryZipMetadataGuard20261024_0400.mjs`) rejects normalized filename collisions and unsafe host file types. The CRC guard (`factoryZipCrcGuard20261024_0500.mjs`) applies tighter limits: 32 MiB input, 8 MiB declared output per entry, and 32 MiB declared output total. It inflates in 16 KiB input blocks, counts observed output, checks CRC-32 and declared size, and independently checks the raw DEFLATE stream end.

The added static resource audit enforces a 16 MiB archive cap, 64 entries, 4 MiB declared output per entry, 16 MiB total declared output and a 100:1 declared expansion ratio. Static archive and entry caps bound **declared** sizes and metadata iteration when checked before allocating or decompressing data. Compression-ratio checks help reject very compact input with disproportionate declared output. The static audit **accepts** maliciously underreported uncompressed sizes if local and central headers agree, because decompression is necessary to establish the truth. Its composed `auditFactoryZipResourceThenCrc20261024_0600` variant compares actual decoded byte counts against declared counts and rejects this forgery. CRC guards detect accidental or hostile changes to decoded content, subject to CRC-32's lack of cryptographic authentication. Resource limits must be enforced against actual decoded bytes as well as metadata, and checked before allocating output buffers.

## Boundaries that static checks do not prove

No JavaScript ZIP parser or in-process budget can guarantee a strict CPU-time limit, peak resident memory, allocator behavior, runtime stability, or resistance to every malicious DEFLATE bitstream. Even a stream constrained by total decoded bytes can expend CPU on malformed codebooks or pathological input. A decompressor may allocate internal buffers independently of the caller's byte counters. A compression ratio threshold is a policy heuristic and can reject legitimate repetitive files; it cannot alone guarantee bounded execution. Declared-size caps do not prove that the declared length is true. A CRC-32 match does not authenticate the sender or certify pattern geometry. This suite uses a 2 MiB expansion fixture to keep local validation bounded; it is no substitute for workload profiling and sandbox limits.

For enforceable resource isolation, process untrusted ZIP input in a dedicated worker **or preferably a separate process** with a real operating-system memory limit, execution deadline/termination, bounded IPC payloads, cancellation, and output quota. In a same-process worker, termination helps limit elapsed work but does not provide the same hard resident-memory isolation as an externally constrained process. Monitor memory, CPU, maximum entry count, observed decoded bytes, and termination behavior under platform-specific stress tests before deployment.

## Integration and manufacturing blockers

The new resource budget audit must be called on every actual ZIP import/export and external ingestion route before downstream parsing, extraction, or writing; relying on stand-alone tests or optional callbacks is insufficient. The guard must never be publicly bypassable by an injected successful audit. Treat all failures and exceptions as `ok: false`, with `manufacturingApproved: false`, and preserve the source bytes. Confirm compatibility with six graded sizes and production-sized input. Independently verify true DXF geometry, units, pattern identity, grade rules, marker quantities, boundary clearance, overlaps, grainlines, seam allowances, techpack dimensions, and factory round trips. Obtain a real manufacturing or downstream CAD acceptance run and sign-off separately. Neither this document nor passing archive resource tests establishes factory readiness or product safety.

The repository's generated six-size Foundation Tee package currently has 60 entries and approximately 649 KiB of STORE-compressed bytes (1:1 ratio). That package is accepted by the independent resource-plus-CRC composition. The 64-entry policy leaves space for only four additional entries before refusing an otherwise structurally valid factory package; this is a **compatibility limitation / potential false positive** as export inventory evolves, not an archive security bypass. A compressed valid file exceeding the 100:1 threshold is likewise refused as a policy false positive, rather than mistaken for corruption. Budget policy changes should be measured against real packages before deployment.
